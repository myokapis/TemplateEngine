# TemplateEngine Improvement Backlog

Generated by comparing `MyOkapis.TemplateEngine` against `Payment.Message`, a proof-of-concept
that started as a fork of this library's ideas and evolved into a fixed-width/XML/JSON payment
message serializer for a different codebase. The domains diverged, but the architectural
patterns Payment.Message settled on are directly applicable back to this library. Nothing here
has been implemented — this is a prioritized list to work from.

## Quick wins (low risk, no breaking API changes)

**Status: items 1-3 below are implemented.** `TrueValues` is now an immutable class with a
`Default` singleton (ordinal comparison, `HashSet<string>`); `ViewModelAccessor<T>` caches each
property's resolved `FormatAttribute` alongside its `PropertyInfo` in a single `Lazy<>`-computed
array instead of re-reflecting per field access; `ImplicitUsings` is enabled on all four projects.

### 1. Replace `TrueValues`'s global mutable static state
**Where:** [`MyOkapis.TemplateEngine/Writer/TrueValues.cs`](MyOkapis.TemplateEngine/Writer/TrueValues.cs), used by
[`WebWriter.SetWebFields`](MyOkapis.TemplateEngine/Web/WebWriter.cs) to decide whether a bound value
renders a checkbox as `checked`.

Two real problems, not just the test-isolation symptom already patched in `TrueValuesTests`:
- `public static List<string> Values { get; set; }` is process-wide mutable state. In a
  concurrently-serving ASP.NET Core app, one caller mutating `TrueValues.Values` changes checkbox
  rendering for every other in-flight request. This is a live concurrency bug, not just a test
  smell.
- `Contains` compares with `StringComparison.CurrentCultureIgnoreCase` against a fixed ASCII
  token set (`"Yes"`, `"Y"`, `"T"`, `"True"`, `"1"`). That should be `OrdinalIgnoreCase` —
  culture-aware casing has no business governing a hardcoded boolean-token check.

**Recommendation:** follow the pattern Payment.Message uses throughout (`SerializationOptions`,
`JsonSerializationOptions`, `XmlSerializationOptions`) — pass configuration explicitly rather than
mutate ambient statics.
- Make the default set an immutable `HashSet<string>` with `StringComparer.OrdinalIgnoreCase`
  (gives correct comparison semantics and dedupe for free, and O(1) lookup instead of O(n)).
- Move "what counts as true" to be instance/writer-scoped (e.g. a property on
  `TemplateEngineSettings` or a constructor parameter on `WebWriter`), not a bare global static.
  If a process-wide default is still wanted for convenience, keep it as a read-only default that
  a writer instance can override, never a mutable shared list.

### 2. Cache format-attribute lookups alongside `PropertyInfo`
**Where:** [`ViewModelAccessor<T>.FormatValue`](MyOkapis.TemplateEngine/Writer/ViewModelAccessor.cs)

`ViewModelAccessor<T>` already caches `PropertyInfo[]` via `Lazy<PropertyInfo[]>` — good, this is
the same pattern Payment.Message uses in `AccessibleMessage<T>` (`Lazy<FieldDefinition[]>` with
`LazyThreadSafetyMode.ExecutionAndPublication`). But `FormatValue` re-does
`Attribute.GetCustomAttribute(pi, typeof(FormatAttribute))` via reflection on every single field
access. Payment.Message avoids this by bundling `PropertyInfo` + `FormatAttribute` +
`SerializationAttribute` into one cached `FieldDefinition` struct fetched once per type.

**Recommendation:** introduce an equivalent `FieldDefinition`-style readonly struct
(`PropertyInfo` + resolved `FormatAttribute`) computed once inside the existing `Lazy<...>`
initializer, instead of re-reflecting per field access.

### 3. Enable `ImplicitUsings`
Trivial cleanup to match Payment.Message's project style; reduces boilerplate `using` blocks
across the codebase.

## Medium (some design change, minor API surface growth — additive, not breaking)

### 4. Decouple "how to format" from "what format to apply"
**Where:** [`Formatters/FormatAttribute.cs`](MyOkapis.TemplateEngine/Formatters/FormatAttribute.cs) and its
five subclasses (`FormatCurrencyAttribute`, `FormatDateAttribute`, etc.)

Today each `FormatXxxAttribute` subclass both declares metadata *and* implements
`FormatData(object)` itself — formatting logic is scattered across five attribute classes, none
of which can be unit-tested independent of the attribute mechanism, none of which are mockable
via DI.

Payment.Message splits this cleanly: `FormatAttribute`/`IFormatAttribute` are pure metadata
(`FormatString`, `Justify`, `MinLength`, `MaxLength`, `PaddingChar`), and a separate injectable
`IFormatter` service (typed overloads for `char`/`DateTime`/`decimal`/`int`/`string`/etc.,
dispatched via a `switch` in the `object` overload) owns the actual formatting logic.

**Recommendation:** extract an `IFormatter`/`Formatter` service in TemplateEngine along the same
lines. Existing `FormatXxxAttribute` classes become metadata-only (or get deprecated in favor of
constructing the metadata directly), and formatting logic becomes centrally testable and
swappable.

### 5. Add padding/justification to format attributes
Payment.Message's `FormatAttribute` base carries `MinLength`, `MaxLength`, `Justify`
(left/right/center), and `PaddingChar`, with validated once-only setters (throws if you try to
set `MaxLength` after `FixedLength` already fixed it, etc.). TemplateEngine's formatters have no
padding/justification concept at all today, despite the README's own claim that the library "can
be used for other purposes where data needs to be merged into a text document" — i.e. non-HTML,
fixed-width text output is an explicitly claimed use case that the formatter API doesn't actually
support yet.

**Recommendation:** if fixed-width text generation is a use case worth keeping, port this
min/max-length + justify + padding-char design onto the format attribute base.

## Larger (breaking API changes — needs a major version bump, evaluate case by case)

### 6. Split `ITemplateWriter` into smaller interfaces
`ITemplateWriter` currently has ~30 members covering four distinct concerns: section
navigation (`SelectSection`/`DeselectSection`/`AppendSection`/`AppendAll`), field binding
(`SetField`/`SetSectionFields`/`SetMultiSectionFields`), field-provider registration
(`RegisterFieldProvider`/`SelectProvider`), and content rendering (`GetContent`). Payment.Message
segregates serializer interfaces by concern (`IMessageSerializer`, `IJsonMessageSerializer`,
`IXmlMessageSerializer`, `IStringMessageSerializer`).

**Recommendation:** consider splitting into narrower interfaces (e.g. `ISectionNavigator`,
`IFieldBinder`, `IContentRenderer`) that `ITemplateWriter` composes. This is a genuine breaking
change for any consumer implementing or mocking `ITemplateWriter` directly, so it should wait for
a major version and needs a compatibility/migration plan, not a quick win.

### 7. Separate "bind POCO to fields" from "writer/section navigation"
Payment.Message's `Mapper<TContext, TMessage>` / `ParentMapper` cleanly separate "map a context
object into a message" from message serialization. TemplateEngine instead bakes POCO binding
directly into `TemplateWriter.SetSectionFields`/`SetMultiSectionFields`, mixing reflection-based
data binding with section append/deselect state management in the same class.

**Recommendation:** worth considering for a future major version, but this is a substantial
refactor of `TemplateWriter`'s core and would break existing consumers' usage patterns. Lower
priority than items 4-6 unless there's a concrete pain point driving it.

### 8. Consider a masking/sensitive-field feature (speculative — only if there's a real use case)
Payment.Message's `SerializationAttribute` (`Masked`, `MaskChar`) lets a field be redacted during
serialization — e.g. for logging payment messages without exposing PANs. TemplateEngine has no
analogous concept. This might be useful if TemplateEngine templates ever render
PII/sensitive data (e.g. masking an SSN field in a debug/log view), but there's no evidence of
that need today — flagging as speculative, not recommended unless a concrete scenario justifies
it.

## Explicitly not portable
- `LrcCalculator` (payment-message checksum utility) — payment-protocol-specific, no analog in a
  text templating engine.
- `IJsonMessageSerializer`/`IXmlMessageSerializer`/`JsonSerializationOptions`/
  `XmlSerializationOptions` — TemplateEngine renders text/HTML, not structured JSON/XML documents;
  not applicable as-is, though the *general pattern* of explicit options objects (item 1's
  recommendation) is still worth adopting.
