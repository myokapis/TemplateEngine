# TemplateEngine Improvement Backlog

Generated by comparing `MyOkapis.TemplateEngine` against `Payment.Message`, a proof-of-concept
that started as a fork of this library's ideas and evolved into a fixed-width/XML/JSON payment
message serializer for a different codebase. The architectural patterns Payment.Message settled
on are the reference point throughout — reimplemented fresh here, not copied, since Payment.Message
is separately-owned code.

## Done: package restructuring + formatting decoupling (items 1-5)

The solution is now five packages instead of two:

```
MyOkapis.ObjectAccess        MyOkapis.Formatting
 (reflected-property              (format attributes +
  metadata, cached,                IFormatter service —
  attribute-agnostic)              no reflection at all)
        \                              /
         \                            /
          MyOkapis.TemplateEngine (Document + Writer + Loader)
                       |
          MyOkapis.TemplateEngine.Web (WebWriter, checkboxes,
                       |                dropdowns, HTML encoding)
          MyOkapis.TemplateEngine.AspNetCore (DI extensions)
```

- **`MyOkapis.ObjectAccess`** — `AccessibleObject<T>`/`FieldDescriptor`: cached, reflection-based
  property discovery with generic `GetAttribute<T>()` lookup. No knowledge of formatting exists
  here at all.
- **`MyOkapis.Formatting`** — `IFormatAttribute`/`FormatAttribute` (pure metadata: `FormatString`,
  `FormatProvider`, `MinLength`, `MaxLength`, `Justify`, `PaddingChar`, with the validated
  once-only setters ported from Payment.Message's design) and `IFormatter`/`Formatter` (the actual
  value → string conversion, leaning on `IFormattable` rather than a per-type switch). Usable with
  no reflection involved at all — formats a raw value with an optional attribute, full stop.
- **`MyOkapis.TemplateEngine`** — `ViewModelAccessor<T>` is now a thin composition of the two
  foundation packages instead of owning both concerns; it no longer does its own reflection or
  formatting logic.
- **`MyOkapis.TemplateEngine.Web`** — carved out of the old `Web/` folder (mechanical move,
  namespace unchanged, so no consumer `.cs` file needed to change — only `.csproj` references).
- **`MyOkapis.TemplateEngine.AspNetCore`** — unchanged in concept, now depends on `.Web`.

This closes backlog items 1-5 from the original list:
1. ~~Replace `TrueValues`'s global mutable static state~~ — done in a prior pass (immutable class,
   `OrdinalIgnoreCase`, `HashSet<string>`).
2. ~~Cache format-attribute lookups alongside `PropertyInfo`~~ — done: `FieldDescriptor` in
   `MyOkapis.ObjectAccess` caches every custom attribute on a property, not just the format one.
3. ~~Enable `ImplicitUsings`~~ — done, all seven projects.
4. ~~Decouple "how to format" from "what format to apply"~~ — done: `FormatAttribute` is metadata
   only, `Formatter` owns the conversion.
5. ~~Add padding/justification to format attributes~~ — done: `MinLength`/`MaxLength`/`Justify`/
   `PaddingChar` are on `IFormatAttribute`, applied by `Formatter`.

One behavior decision worth recording: `Formatter`'s fallback when no `FormatProvider` is supplied
is `CultureInfo.CurrentCulture` (matching the original `value.ToString()` behavior), **not**
`CultureInfo.InvariantCulture` the way Payment.Message does it. That was a deliberate divergence —
Payment.Message's invariant-culture default exists because payment messages are machine-parsed and
need deterministic output; TemplateEngine renders human-facing text, where ambient-culture
formatting is the correct default. Don't "fix" this to match Payment.Message without re-checking
that reasoning.

## Larger (breaking API changes — needs a major version bump, evaluate case by case)

### 6. Split `ITemplateWriter` into smaller interfaces
`ITemplateWriter` currently has ~30 members covering four distinct concerns: section
navigation (`SelectSection`/`DeselectSection`/`AppendSection`/`AppendAll`), field binding
(`SetField`/`SetSectionFields`/`SetMultiSectionFields`), field-provider registration
(`RegisterFieldProvider`/`SelectProvider`), and content rendering (`GetContent`). Payment.Message
segregates serializer interfaces by concern (`IMessageSerializer`, `IJsonMessageSerializer`,
`IXmlMessageSerializer`, `IStringMessageSerializer`).

**Recommendation:** consider splitting into narrower interfaces (e.g. `ISectionNavigator`,
`IFieldBinder`, `IContentRenderer`) that `ITemplateWriter` composes. This is a genuine breaking
change for any consumer implementing or mocking `ITemplateWriter` directly, so it should wait for
a major version and needs a compatibility/migration plan, not a quick win.

### 7. Separate "bind POCO to fields" from "writer/section navigation"
Payment.Message's `Mapper<TContext, TMessage>` / `ParentMapper` cleanly separate "map a context
object into a message" from message serialization. TemplateEngine instead bakes POCO binding
directly into `TemplateWriter.SetSectionFields`/`SetMultiSectionFields`, mixing reflection-based
data binding with section append/deselect state management in the same class.

**Recommendation:** worth considering for a future major version, but this is a substantial
refactor of `TemplateWriter`'s core and would break existing consumers' usage patterns. Lower
priority than items 6/9 unless there's a concrete pain point driving it.

### 8. Consider a masking/sensitive-field feature (speculative — only if there's a real use case)
Payment.Message's `SerializationAttribute` (`Masked`, `MaskChar`) lets a field be redacted during
serialization — e.g. for logging payment messages without exposing PANs. TemplateEngine has no
analogous concept. This might be useful if TemplateEngine templates ever render
PII/sensitive data (e.g. masking an SSN field in a debug/log view), but there's no evidence of
that need today — flagging as speculative, not recommended unless a concrete scenario justifies
it.

### 9. Rethink `FieldDefinitions` (flagged, not yet scoped)
**Where:** [`MyOkapis.TemplateEngine.Web/FieldDefinitions.cs`](MyOkapis.TemplateEngine.Web/FieldDefinitions.cs)

Explicitly called out as needing a redesign. The Web split (this pass) moved it mechanically into
its own package without changing its design — the actual rethink is still open. Worth revisiting
once there's a clearer sense of what's wrong with it (the constructor-string-based checkbox/dropdown
field registration is the likely starting point, but this needs its own scoping pass rather than
guessing at a fix here).

### 10. Done: direct-interface-implementation pattern for `MyOkapis.ObjectAccess`
**Where:** `MyOkapis.ObjectAccess/IAccessibleObject.cs`, `AccessibleObjectBase.cs`

Implemented as designed above, as the prerequisite for `MyOkapis.ObjectMapping` and
`MyOkapis.ObjectSerialization` (see below). `AccessibleObjectBase<T>.Fields` delegates to
`AccessibleObject<T>.Fields`, so both patterns share one cache per type; `AccessibleObject<T>`'s
reflection filters out properties declared on `AccessibleObjectBase<T>` itself so its own
`FieldCount`/`FieldDescriptors` bookkeeping doesn't get treated as data. Those two properties are
additionally marked `[NotMapped]`/`[JsonIgnore]`/`[XmlIgnore]`, since `MyOkapis.ObjectSerialization`'s
JSON/XML serializers call directly into `System.Text.Json`/`System.Xml.Serialization`'s own
reflection (not just the curated `FieldDescriptors` list) — without those attributes,
`FieldDescriptors` would leak into serialized output carrying raw `PropertyInfo`, which isn't
serializable at all. `AccessibleObject<T>`'s wrapper pattern is unaffected; both patterns coexist.

## Done: `MyOkapis.ObjectMapping` and `MyOkapis.ObjectSerialization`

Two new packages generalizing Payment.Message's `Mappers/`/`Serializers/` layers — reimplemented
fresh, not copied, with "Payment"/"Message" avoided throughout per the clean-room requirement.

- **`MyOkapis.ObjectMapping`** — `IMapper`/`IMapper<TSource>`, `Mapper<TSource, TTarget>`,
  `CompositeMapper<TSource, TTarget>` (renamed from `ParentMapper`), `MapperFactory<TSource>`.
  Depends only on `MyOkapis.ObjectAccess`. `Mapper<TSource, TTarget>.Map` returns `TTarget` directly
  (stronger typing than Payment.Message's non-generic return), while still satisfying
  `IMapper<TSource>.Map`'s non-generic `IAccessibleObject` return via explicit interface
  implementation, for the polymorphic child-mapper-resolution case `CompositeMapper` needs.
  Deliberately does **not** depend on `MyOkapis.ObjectSerialization` — Payment.Message's
  `ParentMapper.MapValueGroup` (auto-serializing a mapped child into a string) was left out; a
  consumer who wants that composes it themselves by calling a serializer after `MapChild`.
- **`MyOkapis.ObjectSerialization`** — `SerializationAttribute`/`ISerializationAttribute` (masking,
  terminators), `SerializationOptions`/`JsonSerializationOptions`/`XmlSerializationOptions`,
  `ISerializer`/`SerializerBase<TOptions>`, `FlatTextSerializer` (renamed from
  `StringMessageSerializer`), `JsonObjectSerializer`, `XmlObjectSerializer`. Depends on
  `MyOkapis.ObjectAccess` + `MyOkapis.Formatting`. Simpler than Payment.Message's version in one
  respect: since `MyOkapis.Formatting.Formatter` already applies width/justify/truncation (item 5),
  `SerializerBase.FormatField` doesn't need Payment.Message's separate `JustifyValue` step.

`LrcCalculator` (payment-protocol checksum) remains explicitly not portable — no general analog.
